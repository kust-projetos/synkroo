Purpose

Fechar as pendências encontradas na verificação do último trabalho de frontend sem perder alterações locais existentes. O resultado será um conjunto pequeno de commits verificáveis, um build Cloudflare reproduzível e um registro claro do que foi concluído, superseded ou ainda depende de decisão de produto.

Fora do escopo: este plano não encerra sozinho o Plano Mestre do Synkroo. Fases de produto, banco, IA, financeiro e piloto continuam sendo rastreadas no plano mestre.

Problem

A entrega visual do frontend já está no commit 9596a11 e está ativa no Worker, mas a verificação não fecha todos os gates: npm run typecheck acusa duas atribuições inválidas em process.env.NODE_ENV; npm run build:cf não terminou em 20 minutos no Windows; o repositório possui alterações locais fora do commit visual; e os planos de redesign ainda descrevem arquivos que foram removidos ou nunca foram migrados.

Solution

Executar quatro fases curtas. Primeiro proteger a árvore de trabalho. Depois corrigir o teste de autenticação com API de Jest que respeita o tipo readonly. Em seguida tornar o build Cloudflare reproduzível em WSL/Linux e validá-lo com dry-run. Por fim reconciliar as fases do redesign com a arquitetura real: implementar o que continua sendo requisito, ou marcar como superseded o que foi removido de propósito.

Implementation Phases

Ordem obrigatória: executar cada fase de cima para baixo. Não fazer git clean, git reset, stash, checkout ou commit amplo enquanto a árvore de trabalho não for classificada.

[] Phase 0: proteger a árvore de trabalho

Separar o trabalho de correção das alterações locais já existentes. O branch atual contém o commit visual, mas também possui modificações e arquivos não rastreados de segurança, banco, testes e documentação.

0.1. Registrar o estado inicial

  • Executar git status --short --branch, git log -5 --oneline --decorate e git diff --stat; salvar a saída fora do Git.
  • Executar git diff --name-only 9596a11^..9596a11 e confirmar que o escopo visual está no commit 9596a11.
  • Não tocar em arquivos não relacionados sem identificar o autor e a finalidade.

0.2. Isolar a execução

  • Criar um worktree limpo para este plano a partir de 9596a11: git worktree add ../synkroo-pendencias -b fix/pendencias-verificacao 9596a11.
  • Executar todas as correções somente no worktree novo; preservar a árvore original como fonte de alterações pendentes.
  • Se o worktree não puder ser criado, parar e solicitar decisão antes de alterar o branch atual.

0.3. Testing Strategy

O gate desta fase é de integridade Git, não de aplicação.

  • git status --short --branch — worktree de execução começa limpo.
  • git rev-parse --short HEAD — confirma que a execução começa em 9596a11.
🔁 Não prosseguir se o worktree estiver contaminado ou se alterações da árvore original forem descartadas.

[] Phase 1: corrigir o gate TypeScript

Remover a atribuição direta proibida a process.env.NODE_ENV sem alterar o comportamento testado de cookie seguro.

1.1. Congelar o comportamento esperado

  • Executar npm run typecheck -- --pretty false e confirmar somente os erros nas linhas 167 e 178 de jwt-auth.test.ts.
  • Executar npm test -- --runInBand src/app/api/auth/__tests__/jwt-auth.test.ts e confirmar que a suíte atual continua verde antes da mudança.

1.2. Substituir a mutação direta de ambiente

Em src/app/api/auth/__tests__/jwt-auth.test.ts, substituir o bloco de atribuição por uma propriedade temporariamente substituída pelo Jest:

const nodeEnv = jest.replaceProperty(process.env, 'NODE_ENV', 'production');
try {
  const response = await loginEndpoint.POST(request);
  expect(response.headers.get('set-cookie'))
    .toContain('__Secure-next-auth.session-token=');
} finally {
  nodeEnv.restore();
}

Aplicar o mesmo padrão ao segundo bloco de teste que atribui process.env.NODE_ENV. Não usar as any e não relaxar o tsconfig.json.

1.3. Testing Strategy

  • npm test -- --runInBand src/app/api/auth/__tests__/jwt-auth.test.ts — preserva o contrato de cookie de produção.
  • npm run typecheck -- --pretty false — elimina os dois erros sem esconder testes do compilador.
  • npm run lint — garante que a correção segue as regras do projeto.
🔁 Se jest.replaceProperty não puder substituir NODE_ENV no runtime de Jest, usar um helper tipado com Object.defineProperty e cobrir restore em finally; não aceitar workaround que desative o typecheck.

[] Phase 2: tornar o build Cloudflare reproduzível

O build Next normal passa, mas o build OpenNext/Cloudflare travou depois da geração Next no Windows. A execução oficial deve ocorrer em WSL/Linux, conforme o warning do OpenNext.

2.1. Documentar o ambiente suportado

  • Criar docs/runbook-cloudflare-build.md com pré-requisitos: Node/npm, WSL2, Docker quando necessário, autenticação Wrangler e secrets fornecidos por ambiente, nunca por argumento.
  • Documentar o diretório WSL: /mnt/d/projetos/synkroo.
  • Documentar que wrangler deve ser chamado via npx wrangler, pois o binário global não está disponível no shell atual.

2.2. Criar o gate local de CF

Adicionar ao package.json o script abaixo, sem fazer deploy real:

"verify:cf": "npm run build:cf && npx wrangler deploy --dry-run --config wrangler.toml"

O dry-run deve validar o bundle produzido, bindings e configuração sem publicar uma nova versão.

2.3. Executar no WSL

npm ci
npx wrangler --version
npm run lint
npm run typecheck
npm run verify:cf
  • Confirmar que .open-next/worker.js existe após o build.
  • Confirmar que globalThis.pg = pg e globalThis.__SYNKROO_HYPERDRIVE foram injetados pelo script.
  • Registrar o tamanho comprimido do bundle e comparar com o limite pago configurado no projeto.
  • Registrar o warning de direct mode queue; se continuar, abrir decisão explícita sobre Queue/outbox antes de chamar o release production-ready.

2.4. Testing Strategy

  • npm run build:cf — produz o Worker OpenNext e executa a injeção de runtime.
  • npx wrangler deploy --dry-run --config wrangler.toml — valida upload, bindings e bundle sem alterar produção.
  • npx wrangler check startup — mede startup e identifica regressões de Worker.
🔁 Se o OpenNext travar novamente, capturar o último diretório gerado e o log completo no WSL. Não aumentar timeout indefinidamente no Windows e não declarar o gate verde por causa do next build isolado.

Questionables

O chat widget deve voltar?

Recomendação: não reintroduzir automaticamente. O código legado foi removido e o plano atual não prova que o widget ainda é requisito. Se o produto exigir chat público, a implementação deve nascer de um ADR com pipeline, autenticação de clínica, rate limit e fallback definidos.

Devemos corrigir o build Cloudflare no Windows?

Recomendação: não. O OpenNext explicitamente sinaliza compatibilidade incompleta no Windows. WSL/Linux deve ser o ambiente oficial; o ganho é um gate reproduzível sem criar um wrapper frágil para um ambiente não suportado.

O plano inteiro de redesign deve ser marcado como concluído?

Somente após fechar ou superseder cada item das fases 7 e 8. O landing e o shell já estão entregues, mas páginas e componentes previstos no documento não podem ser considerados concluídos sem implementação ou decisão registrada.
